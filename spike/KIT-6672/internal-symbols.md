## Verdict

Yes, @coveo/headless-ssr can use @coveo/headless as an external dependency plus one internal subpath without breaking because of duplicated state.

ESM (dist/esm, per-file tsc output): no duplication at all, as long as './ssr-internal' maps to a file in the same dist/esm tree (e.g. dist/esm/ssr-internal.index.js). '@coveo/headless', '@coveo/headless/commerce' and '@coveo/headless/ssr-internal' then resolve to the same module instances (state-key.js, utils/errors.js, slices, selectors).

CJS (one esbuild bundle per entry, packages external): the internal entry (B) gets its own copies of every internal module SSR reaches. That is stateKey, loadReducerError, the slice reducers, the reselect selectors, the bueno schema values, the logger factory, utils, the serializers, and possibly a dead copy of the relay selector and coveo.analytics. None of these handoffs breaks, because every value that crosses between bundle A (engine and controllers) and bundle B (SSR helpers) is identity-free:
(1) stateKey is Symbol.for (app/state-key.ts:4), so B's `engine[stateKey]` (commerce facet-generator.ssr.ts:170) and B's `get [stateKey]` override on the spread, redacted engine (commerce build-factory.ts:96-101) hit the same key A uses. If it were Symbol(), A's controllers would read undefined and redactEngine would log the "loading Headless twice" warning.
(2) Reducers from B go into A's per-engine reducer manager, keyed by string names, first wins (reducer-manager.ts, engine.ts:303-309). Both copies react to the same action type strings.
(3) The wait-for-action middlewares from B match action types by regex.
(4) Selectors from B read plain state. The only cost is duplicated memo caches.
(5) Token-expiry detection compares error.name, not instanceof (renew-access-token-middleware.ts:184). Renewal state is in a closure per engine.
(6) The instanceof checks that do exist (DisconnectedError, URLSearchParams, Function) all stay inside one bundle or test a runtime global.
(7) The real module-level singletons (the answerApi RTK Query api and the relay LRU selector) are used only by bundle A.
There are no top-level let/var, globalThis writes or mutable module-level Maps or registries anywhere in non-test headless src. The current CJS layout is already worse: dist/cjs/ssr-next/headless.cjs embeds a whole second engine.

Mitigations to put in the plan:
(a) Keep stateKey as Symbol.for and add a test that guards it.
(b) Allowlist what ssr-internal exports: pure functions, reducers, selectors, schemas and types. Never export class-with-instanceof values, Symbol() keys, RTK Query apis (answerApi) or the relay selector, and never compare loadReducerError by identity.
(c) Pin @coveo/headless exactly (peer plus dependency) in @coveo/headless-ssr, so B's reducers and A's action creators can't drift apart.
(d) Optional, to remove CJS duplication entirely: emit the ssr-internal CJS from the main bundle, by putting the internal symbols in a hidden export of dist/cjs/headless.cjs and having ssr-internal's require condition re-export them. Or ship @coveo/headless-ssr as ESM-only, where nothing is duplicated.
(e) Inside the new package: if it keeps per-entry CJS bundles, its own AUGMENTED_MARKER should become Symbol.for, and consumers should match the named errors by .name, not instanceof. The usual dual-package hazard (an app mixing require and import of @coveo/headless) remains, but it is harmless for the same reasons as above.
