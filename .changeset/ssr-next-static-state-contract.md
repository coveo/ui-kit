In the experimental SSR sub-packages, every engine definition fulfils one plain contract, the new `EngineDefinition<TStaticState, THydratedState, TFetchOptions>` type: `fetchStaticState()` returns the static state, and `hydrateStaticState()` takes it as is, even when a controller requires props (the static state carries them under `controllerProps`, search included). Use it to type code that works with any definition, with two plain type parameters that are inferred from the definition passed in. The states are named after what you wrote: `CommerceStaticState` and `CommerceHydratedState` take the controllers of the definition and its solution type, `SearchStaticState` and `SearchHydratedState` take the controllers, and their `controllers` member spells out the controllers of the page by name, so editor tooltips and compiler errors list them. The `HydratedState`, `FetchStaticState`, `HydrateStaticState`, `HydrateStaticStateOptions` and `CommerceEngineDefinitionBuildResult` types are removed, and `SearchEngineDefinition` and `EngineStaticState` each lose a type parameter. The engine definition options no longer accept a `navigatorContextProvider`, which was ignored: pass the `navigatorContext` to `fetchStaticState()`. The commerce `searchParams` option is optional, as it already was at runtime. See the upgrade guide, "Engine definition types".
